Modelo RIPS/RDA conceptual → FHIR México

Ubicación arquitectónica de extractos tipo RIPS/RDA convertidos a FHIR SUS-RDA-MX.

Canonical URL: https://fhir.sus-rda-mx.local
Version: 0.3.0
Borrador al 2026-10-07
Computable Name: RIPSRDAMX
PROVISIONAL · datos sintéticos. Esta guía experimental no es un estándar oficial mexicano. México/SUS es el único dominio objetivo; Colombia se conserva exclusivamente como REFERENCE_PATTERN. No contiene PHI/PII.

Propósito#

Documentar dónde se colocan los extractos clínico-administrativos tipo RIPS/RDA convertidos a FHIR dentro de la arquitectura SUS México. Esta página es PROVISIONAL, usa solo datos sintéticos y no declara estándar oficial mexicano.

Posición normativa#

  • RIPS/RDA Colombia es REFERENCE_PATTERN.
  • No es norma mexicana.
  • No se adoptan catálogos colombianos como oficiales mexicanos.
  • No se adopta FEV-RIPS como modelo financiero de origen.
  • Se usa el patrón RIPS/RDA para identificar datos clínico-administrativos mínimos que pueden estructurarse en FHIR.
  • México requiere definición oficial propia de catálogos, terminologías, reglas, tarifas y autoridad funcional.

Modelo propuesto México#

  • SUS-RDA-MX es el documento/evento clínico-administrativo FHIR propuesto para México.
  • SUSCrossCareBundle es el paquete de radicación ante la Cámara.
  • SUSCrossCareClaim es el ancla administrativa/operativa de radicación compensable.
  • SUSCrossCareClaim puede referenciar un SUS-RDA-MX aceptado o incluir evidencia mínima estructurada.
  • La radicación inicial no contiene montos de origen: no unitPrice, no net, no total.
  • La valoración económica ocurre después por la Cámara.
  • CFDI/pago ocurre en fases posteriores.

Diagrama textual#

HIS / EHR / farmacia / laboratorio / admisiones del prestador
  -> Extracto clínico-administrativo tipo RIPS/RDA conceptual
  -> Transformación FHIR SUS-RDA-MX
  -> SUSCrossCareBundle + SUSCrossCareClaim sin montos
  -> Cámara de Compensación
  -> FHIR Server
  -> Workflow operacional PostgreSQL
  -> Reglas / auditoría / vista 360 / valoración posterior

Ubicación arquitectónica#

  1. Sistema fuente del prestador: HIS/EHR/farmacia/laboratorio/admisiones generan extracto clínico-administrativo; ese extracto puede parecerse conceptualmente a RIPS/RDA y se transforma a FHIR.
  2. SUS-RDA-MX: documento/evento clínico-administrativo FHIR propuesto para México; puede contener evidencia clínica estructurada y ser referenciado por la radicación.
  3. SUSCrossCareBundle: paquete ante Cámara con Claim + evidencia mínima + Provenance; puede incluir o referenciar SUS-RDA-MX; sin montos de origen.
  4. FHIR Server: guarda recursos FHIR aceptados y se consulta por API FHIR; los dominios de negocio no acceden por SQL directo.
  5. PostgreSQL operacional: guarda submission_id, radicado, estados, reglas, resultados, timeline y referencias FHIR; no duplica payload clínico completo y no es servidor FHIR.
  6. Vista 360: compone recursos FHIR autorizados y datos contextuales mínimos; no es historia clínica completa; apoya auditoría y decisión institucional.
  7. Valoración: usa servicios, cantidades asistenciales, CUBS/catálogo y reglas; los montos se calculan después por la Cámara y no son suministrados por el prestador.

Relación con vista 360#

  • La vista 360 puede usar datos transformados a FHIR desde fuentes tipo RIPS/RDA.
  • No debe enviar todo el expediente clínico.
  • Debe aplicar minimización, autorización, trazabilidad y segregación institucional.
  • Sirve para auditoría y contexto de la institución responsable.

Relación con terminologías#

  • ICD-10 / clasificacion diagnostica adicional fuera de Fase 0 readiness para diagnósticos.
  • catalogo clinico mexicano pendiente como granularidad clínica candidata.
  • catalogo mexicano de observaciones pendiente como observaciones/laboratorio candidato.
  • catalogo mexicano de medicamentos pendiente como medicamentos candidato.
  • CUBS/catálogo mexicano como servicio compensable/tarifa.
  • CLUES como establecimiento.
  • CURP/identificador alternativo como identidad.
  • Catálogos institucionales como mapeos futuros.

Relación con reglas técnicas#

El modelo RIPS/RDA→FHIR ayuda a validar presencia de diagnóstico, evidencia mínima, procedimiento asociado, medicamentos/suministros, vacunación, CLUES, CUBS/categoría de servicio, ausencia de montos de origen y consistencia entre Encounter, Condition, Procedure, DiagnosticReport, MedicationRequest, MedicationDispense e Immunization.

Impacto en estimación#

Este modelo permite estimar interfaces con prestadores, transformadores RIPS/RDA conceptual a FHIR, validadores FHIR, terminología, mapeo de catálogos, almacenamiento FHIR, workflow operacional, vista 360, reglas de validación, auditoría y valoración posterior.

Resumen para implementadores#

Tratar RIPS/RDA Colombia como patrón de análisis, no como norma mexicana. Transformar extractos clínico-administrativos mínimos a FHIR, radicar con SUSCrossCareBundle/SUSCrossCareClaim, persistir FHIR aceptado en FHIR Server y mantener el workflow operacional en PostgreSQL operacional sin duplicar payload clínico completo ni aceptar montos de origen.
